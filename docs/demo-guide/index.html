What the demo is

A small workbench for developing a candidate procedure from evidence. A drafting step proposes steps and claims, and every claim cites an exact passage in a versioned source. Code checks the citations, dates and records. A named reviewer judges whether each passage supports its claim and decides on one exact version. When a source requirement changes, the workbench marks the accepted version stale, shows which conclusions need reassessment, and refuses to reuse the old acceptance.

The scenario is an invented inspection of a portable sensor kit (PSK-7). It is shaped like tactics, techniques and procedures development, but it is not an Air Force process and approves nothing operationally.

What is real and what is simulated

Real and testedVersioned sources with hashes, citation and date checks, the review gate, stale detection, change impact, audit log, 20 automated tests, 18-case evaluation
SimulatedThe drafting step: a deterministic program with one planted error. It is not AI.
SimulatedThe system-model data: hand-written JSON. No Cameo connection.
Not exercisedThe live Claude adapter exists in the code but has never run (no API key). It is disabled in the hosted build.

How to use it

The five tabs

  • 1 Sources: the eight synthetic sources with revision and hash, an inbox of changes to import, and the Generate button
  • 2 Candidate & review: the draft, the evidence panel, the automated checks, reviewer judgments and the accept, request-changes and reject decisions
  • 3 Change impact: the verdict after a change: what changed, what to reassess, which result flipped, and whether the acceptance still applies
  • 4 Runs & evaluation: every generation run and its settings, plus the evaluation suite
  • 5 History: the append-only audit log

Controls to know

  • Acting as (top right) switches between demo identities. Keep it on R. Alvarez (reviewer). J. Kim (author) shows that authors cannot accept.
  • Presenter guide (#guide): seven steps that tick off as you really do them. Go opens the right tab and outlines the next button. The guide never clicks anything for you.
  • Reset to in the guide, or Reset demo in the header, reloads a stage. Click twice to confirm.
  • Tab badges such as STALE and sources changed show where attention is needed.

The core path in seven steps

  1. Sources: click REQ-002@A. It says 180 days.
  2. Generate candidate, then click the red citation on step S7.
  3. Click Accept for demo on v1. The server refuses with 409 REVIEW_BLOCKED.
  4. Import the corrected inspection log and regenerate. Mark C14 does not support, remove it and save as v3. Run the bulk judgment, type a rationale, then accept.
  5. Import REQ-002 revision B (180 → 90 days). The app opens Change impact.
  6. Click Try to reuse this acceptance. The refusal, 409 EXPORT_BLOCKED, appears under the button.
  7. Show 4 Runs & evaluation and 5 History.

Before the call

Set up (10 minutes before)

  • Open the GitHub Pages link with #guide in its own browser window. Share only that window in Teams, not the whole screen.
  • Set browser zoom to 125%. Close other tabs and notifications.
  • Open a second tab with #reviewed,guide as a backup.
  • Have the repo open in an editor at server/workbench.js, function decide, for the code segment.
  • Optional: a terminal with npm run demo:walkthrough ready.

Say these limits early

  • All data is synthetic. It is not a TTP and not an Air Force process.
  • The drafting step is a deterministic stand-in with one planted error, not AI.
  • No Cameo connection; the model data is hand-written.
  • How it was built: decide beforehand how you describe your part and the AI assistant's part (packet section H.4).

10-minute walkthrough with transcript

Each segment lists what to do, what appears on screen, and what to say. Speak in your own words; the transcript is a guide, not a script to read. About 850 spoken words, leaving time for clicks.

0:00–1:00
Framing
Do
Stay on 1 Sources with the guide strip visible.
On screen
Eight sources, the badges SYNTHETIC DATA and Simulated system-model export.

"Gus, you mentioned that AI-assisted development of tactics, techniques and procedures is a differentiator, so I built a small prototype around how I would approach it as an engineer. Everything here is synthetic: an invented sensor kit, three made-up requirements, some inspection records, and a hand-written stand-in for a system-model export. It is not a TTP, it doesn't connect to Cameo, and it approves nothing. What I want to show is the workflow around an AI draft, because that's where I think both the risk and the value are."

1:00–2:00
Sources and the first draft
Do
Click REQ-002@A. Then click Generate candidate.
On screen
Passage p1 says 180 days; structured field maxCalibrationAgeDays: 180. Then v1 DRAFT with 5 blocking findings, run labeled SIMULATED · not AI.

"Each source is an immutable snapshot with an id, a revision and a content hash. This requirement says calibration is current within 180 days, and that number is also stored as a field that code can use."

"Now I'll ask for a candidate procedure. The drafting step in this demo is a deterministic stand-in, not a model, so the demo is repeatable offline, and it has one error planted on purpose. The draft has steps, claims with citations, assumptions, a hypothesis clearly labeled as one, and two things it couldn't resolve: a missing battery observation and a serial-number conflict between two records."

2:00–3:00
The planted error and the server gate
Do
Click the red citation on S7. Then click Accept for demo.
On screen
Evidence panel: quote not in passage. Then 409 REVIEW_BLOCKED with the list of reasons.

"Here's the planted error: a plausible cleaning step. The citation is red because the quoted text isn't in the cited passage. Code can check that a citation exists. It can't check that a quote actually supports a claim; that's the reviewer's job, and the screen keeps those two things separate."

"If I try to accept anyway, the server refuses and lists why. The browser can't send 'approved'. The server works it out again from stored state."

3:00–4:30
Evidence closes gaps; the reviewer closes claims
Do
Import Corrected inspection log, regenerate, mark C14 does not support, remove, add an edit note, Save as new version. Click the demo-shortcut bulk judgment, type a rationale such as "C14 removed; remaining citations resolve", Accept for demo.
On screen
"1 candidate version marked STALE". v2 still has the fake step. The edit creates v3 NEEDS_REVIEW, then REVIEWED_FOR_DEMO.

"The inspector corrects the log. Importing it doesn't overwrite anything; it becomes revision 2, and version 1 of the draft is now stale because it was built on different sources. I regenerate. The gaps are gone, but the fake step is back, which is realistic: models repeat their mistakes."

"As the reviewer I mark that claim as not supported and remove it. That creates version 3 with its own fingerprint. I judge the remaining claims. I'm using a shortcut here to save time, and it's recorded as a shortcut. Then I accept, with a rationale. The acceptance is tied to this exact version and this exact set of sources."

4:30–6:00
Change one requirement (the key moment)
Do
Import REQ-002 revision B (180 → 90 days). The app opens 3 Change impact. Point at the verdict banner from top to bottom.
On screen
REQ-002@A → REQ-002@B · maxCalibrationAgeDays 180 → 90. Tiles: 2 reassess, 1 re-confirm, 1 step affected of 7, 11 unaffected, 1 computed flip. C6: PASS → FAIL (114 days > 90). A red panel: "R. Alvarez's acceptance for demo no longer applies".

"This is the part I care about most. The requirement changes from 180 days to 90, and I import revision B."

"Top line: what changed. Then the scope. Two conclusions need to be reassessed: the claim quoting the changed sentence, and the computed calibration result, which flips from current to not current because the certificate is 114 days old. One claim needs a quick re-confirmation because its source was revised but its sentence didn't change. One step out of seven is affected, and eleven claims aren't touched."

"And the red panel: the earlier acceptance no longer applies, and it says why."

If the import misfires: open the backup tab, or load #changed.

6:00–6:30
The old acceptance is refused
Do
Click Try to reuse this acceptance (export as reviewed).
On screen
409 EXPORT_BLOCKED under the button, then "Source change: REQ-002@A -> REQ-002@B".

"If someone tries to reuse that old acceptance, it's refused. The history keeps the decision; it just can't be used on sources it never saw."

6:30–7:30
Code: the acceptance gate
Do
Switch to the editor: server/workbench.js, function decide, and acceptReadiness.
On screen
The single transaction that checks permission, digest, manifest, blocking findings and judgments.

"Briefly in code. This is the acceptance function. In one transaction it checks the reviewer's permission, that the version fingerprint the reviewer saw is the stored one, that the sources haven't moved, that no blocking check is open, and that every factual claim has a reviewer judgment. Only then does it look at the rationale, so nothing is ever recorded without one. Every write carries an operation id, and there's a test that kills the server right after it commits and proves the retry returns the saved result instead of a duplicate."

7:30–8:15
Evaluation, including a case built to fail
Do
Open 4 Runs & evaluation, click Run evaluation suite, point at H08. Then 5 History.
On screen
Prototype gate PASS, 0 unsafe outcomes, H08 FAIL_KNOWN_LIMITATION, audit chain verified.

"I evaluated the whole workflow, not just the output. There are eighteen fixed cases, split into development and held-out, run against the stand-in and a simple template, with pass criteria written down before the held-out run. Zero unsafe outcomes: nothing stale, revoked or unauthorized got accepted. The template never flags gaps; the drafting step does, but I wrote that stand-in myself, so that's a test of the harness, not a claim about any model. One case is designed to fail: a real quote attached to the wrong claim passes every automatic check, and only the reviewer catches it. I kept it because it marks the boundary."

8:15–9:15
The main tradeoff, and the link to Gus's work
Do
Stay on History or return to Change impact.
On screen
Nothing new.

"The main tradeoff: I invalidate conservatively. Any source change makes open reviews stale, and then the impact view keeps the re-review small. I'd rather ask an expert to re-confirm something than silently keep an acceptance built on an old requirement."

"The pattern of an authoritative source, generated artifacts and version-bound review seems related to what you described for DMM-C and Digital Forge. Before claiming a fit, though, I'd want to learn how your model data is versioned and who holds approval authority."

9:15–10:00
Limits and a question back
Do
Stop sharing, or leave Change impact on screen.

"What this doesn't show: real model quality, real users, or how the Air Force actually develops tactics. I haven't been able to read DAFMAN 11-260 directly. The next experiment I'd propose is running a live model on the held-out cases with two independent expert reviewers and comparing it against the template."

"A question for you: in your workflows, what is the authoritative source, and what event should force a re-review?"

Q&A transcript (practice)

Likely questions with answers in plain words. The notes mark where to be careful or to say you don't know.

Panel
Who built this?
You
"I wrote the brief: the controls, the states, the test cases and what counts as passing. An AI coding assistant implemented it, and I verified the behavior with the tests, the evaluation suite and by driving the app myself."
Adjust this to what is actually true before the interview. Read decide and runOp so you can explain them line by line.
Panel
A prototype built quickly on synthetic data doesn't show you can lead software across programs.
You
"Agreed, it doesn't show scale. It shows how I frame the problem, where I put the controls, and how I test a claim before making it. My leadership evidence is Stimulus, Salesforce and Zillow, and I'm happy to go deep on any of those."
Panel
Why use AI at all? A template would do.
You
"The template covers every requirement but never flags anything it wasn't told about: it missed the gap and the conflict. The plausible value of AI is connecting evidence across records. Numbers, dates and state transitions stay in code, which is why the calibration check is computed, not generated."
Panel
How do you measure unsupported claims?
You
"Two layers. Code checks that each citation exists and the quote matches exactly. A reviewer judges whether the passage supports the claim, and that's stored separately. The human-judged rate isn't measured yet, and case H08 shows why the automatic layer isn't enough on its own."
Panel
Won't marking everything stale overwhelm reviewers?
You
"It might, and that's the tradeoff I chose. Judgments carry forward for claims that are unchanged word for word, and the reassess and re-confirm split keeps the list short. Filtering staleness by relevance is next, once the dependencies are trustworthy."
Panel
What about security and provenance?
You
"Roles are checked on the server and denials are logged. Decisions are tied to the version and source fingerprints, sources are immutable, and the audit log is hash-chained."
Say plainly: the demo identities aren't real authentication, and a database administrator could still bypass the write protections.
Panel
What if two things happen at once, or the server crashes?
You
"Every write has an operation id stored in the same transaction, so a retry returns the saved result. If a source changes while someone is reviewing, the acceptance is refused as stale. There's a test that kills the process right after commit."
Limits: one process and one SQLite writer, no distributed transactions.
Panel
What would it take to use real Cameo data?
You
"An export with stable element ids and a model revision, agreement on which repository is authoritative, element-level change detection, and a mapping of permissions. I haven't worked with Cameo's interfaces; I'd need to learn which ones you have installed."
Panel
Could this run disconnected?
You
"The prototype runs fully offline in stand-in mode. A disconnected deployment would need an approved on-premises model endpoint behind the same provider interface."
Don't claim any accreditation.
Panel
How would you run a first pilot?
You
"Pick one real, low-risk procedure family with two subject-matter experts. Agree on stop and go criteria first. Pair a developer with an expert to build the test cases, review disagreements weekly, and focus code review on the gate and the state transitions. What would success look like to you?"
