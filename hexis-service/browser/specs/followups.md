# Engine follow-ups (minor findings left after each wave's final verification)

A final engine polish round fixes these or documents them as conservative deviations. Every item was
found by independent differential testing against the Python reference. In each one, JS and Python both
reject the input or the API misuse; they differ only in error class, message or documentation accuracy.

## Wave 1 · models (accepted=False)

* **minor**: For numeric strings of 4300+ digits, JS reports a different pydantic error type than Python. Both reject. JS counts significant digits and uses int_unsafe, while pydantic-core applies its own length rules. This contradicts the claim in deviations/models.md and in the builder's notes that JS error lists are a superset of pydantic's, and the README rule that error codes and categories must match.
  * repro: Transition {"to":"x","support": "-"+"9"*4300}: Python ValidationError [int_parsing_size @ ('support',)]; JS HX.efsm.pyd.validate(HX.efsm.MODELS.Transition, same) -> [int_unsafe @ ['support']]. {"support": " "+"7"*4301}: Python [int_parsing]; JS [int_parsing_size]. {"support": "+"+"1"*4301}: Python [int_parsing]; JS [int_parsing_size]. In a 756-string grid (sign, leading zeros, underscores, .0 suffix, padding, 4297-4303 digits), 342 differ in error type. In none of them does JS accept what Python rejects. Script: /tmp/claude-0/verify-scratch/models/gen_boundary.py.
* **minor**: With a lone-surrogate input key, JS fails the model before validating its fields, but pydantic validates the fields first. So when a nested JudgeAction before-validator raises TypeError, that TypeError escapes in Python, while JS reports only string_unicode and no python_type_error. Both reject, but the error class differs, and models.md says pydantic behaves like JS here.
  * repro: State input {"id":"S","action":{"kind":"judge","prompt":"q","reads":["a"],"writes":["b"],"labels":true},"\ud800":1}: Python State.model_validate raises TypeError("'bool' object is not iterable"); JS pyd.validate(MODELS.State, same) -> errors [["string_unicode", []]] (EfsmError, no python_type_error). Same at Machine level: {"skill_id":"s","initial":"i","\udc00":1,"states":{"A":{"id":"A","action":<that judge>}}}. Script: probe_skey.py.
* **minor**: SupplierRegistry raises a native JS TypeError, not an HX.HXError, for registry keys without '|': dict keys, [key, rec] pairs, 2-character string pairs, or [tenant, ref] keys whose tenant contains '|'. Python's dict() accepts all of these; the records simply never match. This is undocumented. It contradicts models.md ('Python's dict() errors for other values', 'A tenant id that contains | never matches a record') and the stated convention that the fakes raise Python built-in errors as HXError with the Python class name.
  * repro: new HX.fakes.SupplierRegistry({"foo":{"business_unit":"B"}}) -> native TypeError "registry keys must be 'tenant|supplier_ref'". Python SupplierRegistry({'foo': {...}}) constructs, and .lookup({'supplier_ref':'SUP-1','business_unit':'B'}, {'tenant_id':'acme'}) -> {'status':'new','existing':{}}. Same divergence for [["k","v"]], for ["ab"] (Python dict(['ab']) == {'a':'b'}) and for [[["a|b","c"], null]] (Python accepts the key ('a|b','c')).
* **minor**: FixtureExtractionModel, REPAIR_DRAFT with a string draft: Python's dict(str) raises ValueError, or returns {} for an empty string, while JS always raises TypeError. models.md documents only the list-of-pairs case.
  * repro: generate({"kind":"model","state_id":"REPAIR_DRAFT","prompt":"p","inputs":{"draft":"ab","validation_issues":[]},"output_schema":{}}): Python ValueError 'dictionary update sequence element #0 has length 1; 2 is required'; JS HXError code TypeError "cannot convert 'str' object to a dict". With inputs.draft = "": Python returns a ModelResponse with output {'draft': {}} and raw_text '{"draft": {}}'; JS raises TypeError. Found in 153 of 4,000 random model sequences (gen_fakes_b.py).
* **minor**: HX.catalog.py_regex_check reports patterns containing lone surrogates as re.error, but CPython 3.12 re.compile accepts them. This class is not in the documented stricter list, and the helper's documented contract is to answer whether re.compile accepts the pattern. check_schemas cannot reach this case, because load_catalog already rejects lone surrogates under a documented deviation.
  * repro: HX.catalog.py_regex_check("\ud800") -> {kind:"error", message:"lone surrogate in pattern (JS port)"}. Python: re.compile('\ud800') and re.compile('[\udc00-\udfff]') succeed. new RegExp("\ud800","u") also compiles.
* **minor**: deviations/models.md says the free-form-JSON integer-like key reordering has 'no hash impact', and the row says it is not order-tested. That is inaccurate. validate_draft's ordered issues list changes, so its digest changes, and this output is hashed downstream: export_run_trace puts the tool output in each Record (record digests), and checkpoint digests include validation_issues. The reordering itself is documented and cannot be fixed with plain objects; the claim and the missing test are the problem.
  * repro: validate_draft({"draft":{"legal_name":"A","source_links":{"ghost":"D1","12":"D1"}},"required_fields":[]}, {}): Python issue fields ['ghost','12'], digest(output) = sha256:54432b63c93e47c9390b526ebb25b8c8cd6fd19806f5b01a27becdba8f076ca2; JS ['12','ghost'], sha256:59dee1cd88f7e595043c14efb6af6ae1b715a53cbd319c94dade7a9727fc5e02. Of 12,000 random drafts, 970 differ, and every one of them is exactly this reordering.
* **minor**: Convention nit: 25_efsm.js reads another namespace at load time (const util = HX.util), but the README allows only HX.HXError at load time. In practice this is harmless: 00_hx.js always loads first, and 10_canonical.js uses the same pattern.
  * repro: src/25_efsm.js line 28: `const util = HX.util;`. Loading each of the five modules alone after 00_hx.js, and in reverse order, works (verified in a fresh vm context). No Date.now, Math.random, async, timers, DOM, network or storage in any of the five files; each is a single IIFE on globalThis.HX.

## Wave 1 · guards (accepted=True)

* **minor**: Counterexamples from analyze_disjoint can contain integral numbers at or above 2^53, and HX.canonical refuses to canonicalize them. This happens both when the value equals Python's exactly (1e16) and with deviation #6 representatives. Python's validator copies an.counterexample into analyses[] and the GUARDS_OVERLAP finding detail, then digests the report (validate.py:65, 473-477), so a faithful JS validator port will throw CanonicalError where Python returns a report. deviations/guards.md #6 only says the value differs, and the builder's notes for consumers (specs/notes-w1.md) don't mention that these values cannot be digested. This is a documentation and consumer-notes gap: guards' own values are correct (equal to Python's, or in the same region per #6).
  * repro: Input: analyze_disjoint(['x >= 1e16', 'x == 1e16'], {'x': 'integer'}), then digest {'counterexample': an.counterexample} as validate.py does. Python: COUNTEREXAMPLE, edges (0, 1), counterexample {'x': 10000000000000000}; canonical_bytes gives {"counterexample":{"x":10000000000000000}}. JS: COUNTEREXAMPLE, edges [0,1], counterexample {x: 10000000000000000} (same value), but HX.canonical.canonical_text({counterexample}) throws CanonicalError 'integer outside the exactly representable range (+/-(2^53-1))'. Same error for ['x > 1e16', 'x > 2e16'] with {'x': 'integer'}: Python x=20000000000000001, JS x=20000000000000004 (#6).

## Wave 2

* **static · minor**: COUNTER_INIT depends on Python's int/float distinction for Variable.init, which is typed Any. A raw JS object can't carry it. If a counter's init arrives as JSON text 0.0 through plain JSON.parse instead of HX.canonical.strict_loads (for example a draft from a future live compiler, or a hand-built dump), the JS port admits a package that Python rejects. deviations/static.md does not mention this; it lists the integral-float issue only for disjointness counterexamples (#5). It is covered only by the general README rule ('Integral floats ... are rejected by the strict parser. Engine data must not rely on them'). In practice it fails closed: strict_loads rejects '0.0', and a package sealed by Python with init 0.0 gets HASH_MISMATCH in JS. That is why I rate it minor, not a permissive deviation reachable through the sanctioned input path.
  * repro: Take the compiled procurement package and set machine.variables[repair_count].init = 0.0, then reseal. Python: validate_package(MachinePackage.model_validate(d).sealed(), load_catalog()) gives passed=False, codes={COUNTER_INIT}. JS: set init = JSON.parse('0.0') (which is 0), then HX.validate.validate_package(HX.pkg.sealed(HX.pkg.normalize_package(p)), HX.data.tool_catalog) gives passed=true, codes={}. HX.canonical.strict_loads('{"init": 0.0}') throws CANONICAL 'integral float literal 0.0 is not representable'. Suggested fix: add a line to deviations/static.md saying that COUNTER_INIT (and any Any-typed integral float) relies on input going through strict_loads.
* **kernel · major**: 40_kernel.js `_charge` adds budget counters as plain JS numbers and never checks Number.isSafeInteger, so sums above 2^53 come out inexact. `advance` then succeeds and returns a checkpoint whose budget value differs from Python's, and that checkpoint cannot be hashed (HX.canonical throws). The README and PORTING rule is to reject integers beyond +/-(2^53-1) where Python accepts and to document it; here they are silently rounded instead. This is not in deviations/kernel.md. The `inc` path has the same cause (`py_int(after[inc]) + 1` with no range check): the result can reach 2^53, which JS holds exactly, but every later digest or store write throws. The inputs are valid on both sides, since each field is a safe int that new_checkpoint/new_observation accept. They are very unlikely in practice, and the failure surfaces at the next canonicalization.
  * repro: Package with a model state M (a mini package like the builder's, e.g. variables x:string; edge {if:"", to:B}). Checkpoint: RunCheckpoint(tenant_id='t', run_id='r', artifact_hash=<pkg hash>, state_id='M', variables={'c':0,'c2':0}, budget={'tokens': 9007199254740000}). Observation: Observation(run_id='r', state_id='M', revision=0, kind='model', outputs={'x':'a'}, usage={'tokens': 9007199254740991}, failure='f'). Python: status RUNNING, checkpoint.budget.tokens = 18014398509480991. JS: status RUNNING, checkpoint.budget.tokens = 18014398509480992, and K.checkpoint_digest(result.checkpoint) throws CanonicalError. Without failure: both FAILED BUDGET_EXHAUSTED with the same budget difference. Same with tool_calls 9007199254740991 + usage 2: Python 9007199254740993, JS 9007199254740992. Script: /tmp/claude-0/verify-scratch/kernel/v3/budget.py + budget.mjs
* **kernel · minor**: deviations/kernel.md says the TASK_INPUT_INVALID / OUTPUT_SCHEMA verdict equals Python's 'apart from the fail-closed regexes'. In fact, any schema keyword outside HX.jsonschema's subset (propertyNames, minProperties/maxProperties, prefixItems, contains, dependentRequired, $ref/$defs, if/then/else, unevaluated*) also fails closed in the kernel, so every value is rejected where python-jsonschema may accept. This is conservative, but it is not documented for the kernel (models.md only covers it for catalog check_schema).
  * repro: Output contract for variable o: {"type":"object","patternProperties":{"^x\\w*$":{"type":"integer"}},"additionalProperties":{"type":"string","minLength":2},"propertyNames":{"maxLength":3}}; model observation outputs {s:'AB1', n:12.34, o:{'xab':1,'yy':'ab'}}. Python advance: OK, TRANSITION to A. JS: KernelError OUTPUT_SCHEMA "'o' fails its schema: <root>: unsupported schema keyword 'propertyNames'" (45 of 600 schema-package vectors in seed 777 before I removed propertyNames).
* **kernel · minor**: Construction rejects values that are valid JSON but exceed the canonical limits (nesting deeper than about 64, strings longer than 1,048,576 code points) in RunCheckpoint.variables and Observation.outputs, with ValidationError json_invalid. Python accepts the checkpoint and either runs normally (an untouched deep variable), returns FIELD_SCOPE_VIOLATION, or raises CanonicalError later in advance. This is conservative, but kernel.md's row only names lone surrogates, integers beyond 2^53 and 'other non-JSON values', so the docs are imprecise.
  * repro: RunCheckpoint(variables={'doc':{'a':'x','f1':1},'issues':[],'zz':nest(62)}) on the field-scoped package, then advance with outputs {'doc':{'a':'x','f1':1}}. Python: OK (state A). JS: K.new_checkpoint throws ValidationError [json_invalid, ['variables']]. Same pattern with old doc field 'big' = 'a'*1048577: Python FIELD_SCOPE_VIOLATION fields ['big'], JS ValidationError json_invalid.
* **kernel · minor**: KEY_ORDER_UNKNOWN is raised while computing unresolved_effects, before later Python failures, so the error class differs in some cases where Python also rejects.
  * repro: End state X (undeclared terminal). engine={'terminal_admission':{'receipts':True,'unresolved_effects':{'7':2,'z':1}}}. Python: TypeError "'bool' object is not iterable". JS: HXError KEY_ORDER_UNKNOWN.
