Model-to-Evidence Workbench

A security plan generated from a system model is only useful if each statement can be traced to a current source, and if people can see when a model change makes a statement, or a review of it, out of date. This prototype follows one element from the model to a draft SSP paragraph, then changes the model.

Imported descriptions count as assertions. A check result applies only to its stated inputs and versions. Accepting the wording is a document review, not a finding that a control is effective.

The demonstration, in order

Five steps, as recorded

  1. Step 1

    Import model revision A and its evidence

    Four components, three flows, two boundaries. The workbench builds one row per model object and selected control statement.

    Observed: 3 of 4 selected rows have current applicable evidence. AC-3, AU-12 and SC-8 on the portal flow PASS. The database's inherited SC-8 claim stays UNKNOWN because no provider evidence exists.
  2. Step 2

    Withdraw the transport test

    The model still says TLS. The workbench won't let a model attribute stand in for a test.

    Observed: SC-8 portal→API drops to UNKNOWN with the reason “no current applicable observation”. The design assertion is kept. The previous package becomes STALE.
  3. Step 3

    Restore, rebuild, and review

    A reviewer accepts the wording. The decision is bound to the package's exact digest and to the current set of dependencies, and open gaps are recorded as acknowledged limitations.

    Observed: the engineer's own review attempt is denied. The reviewer's ACCEPT succeeds and export produces a Markdown excerpt, an evidence manifest and an OSCAL component definition.
  4. Step 4

    The model changes to revision B

    Revision B adds an external maintenance provider and changes which role may write telemetry.

    Observed: exporting the accepted package as current is refused because it is STALE. The impact view lists, by stable ID: the API changed; a new boundary-crossing flow created a new SC-8 row; two evidence items no longer apply because they were collected against API revision a1. Those reports say PASS and are still not reused.
  5. Step 5

    New evidence for B, rebuild, review

    AC-3 compares the model's declared permissions with a reviewed OPA policy, using tests written from the requirements rather than from the policy.

    Observed: AC-3 FAIL. The model and the reviewed policy disagree about who may write telemetry, which is a finding for a person to resolve. The provider flow's SC-8 row is UNKNOWN (no test). The reviewer accepts the wording with those gaps recorded.
Where AI sits

Drafting inside a review boundary

The drafter proposes text and questions. It sees only permitted, digest-pinned sources, has no tools, and cannot change evidence, review state or policy. A validator checks every claim.

  • A deliberately bad draft with six seeded problems (an uncited claim, an unresolvable citation, an unpermitted source, a fabricated CVE, “compliant with SC-8”, and a line obeying an instruction hidden in a provider document): all six flagged, no review state changed.
  • A plausible generated Rego policy, run in quarantine against the independent tests: fails 5 of 15. The enforcement policy's digest is unchanged. A candidate calling http.send is rejected at compile time.
  • The drafting shown is a deterministic fixture. It demonstrates the controls around AI, not the quality of a language model.
Evaluation

Results on synthetic scenarios

22 of 22 acceptance scenarios passed, each on a fresh database. They cover stale, other-environment and expired evidence, conflicting sources, revoked reviewers, concurrent review, retry after commit, prompt injection, empty policy tests and invalid OSCAL. Verification also caught two real defects in the first version, both fixed.

How it is built

Architecture

Key decisions

  • Conservative invalidation. Any change to model, evidence, catalog, mappings or policy makes a review stale. The impact analysis guides re-review but never keeps an approval alive. A wrong “still reviewed” is the expensive failure.
  • Stable IDs for identity, pointers for citation. Array positions move between revisions; namespaced IDs don't. Pointers stay exact because they cite a digest-pinned snapshot.
  • One applicability rule. Status, environment, expiry and target revision are checked in one place, so “why wasn't this report used” has one answer.
  • Review in one transaction. The reviewer's authority, the digest they saw, freshness and the decision head are re-checked under a write lock, so concurrent reviewers get an explicit conflict.

Limitations

  • No Cameo, Teamwork Cloud or program system is connected. The model format is a documented synthetic JSON contract.
  • Evidence is fictional. Identities are simulated; there is no authentication.
  • Language-model drafting quality is unmeasured. An optional adapter exists but was not run.
  • Control mappings are illustrative and not assessor-validated.
  • Implemented in one session with an AI coding agent from a written specification, then verified with the tests above.
Next

One bounded experiment

Take one authorized model export and one artifact section. Compare AI-assisted drafting with the current template on 16 to 24 packages, with two reviewers and a held-out third of the cases. Measure supported-claim rate, unsupported assertions and reviewer time. Stop if unsupported assertions rise or reviewer time doesn't fall. The same pieces (source identity, citation validation, digest-bound review, staleness on source change) would carry over to an AI-assisted procedure-drafting experiment with subject-matter-expert review.
